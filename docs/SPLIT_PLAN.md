## Как реализовано в 3.0.0 (отличия от плана)

Ответы владельца: оба сервера в Германии, один хостинг, разные подсети; Remnawave 3.4.5, subscription-page 8.0.0;
сотрудники входят по обычному домену панели (без «стука»); один репозиторий; все 9 платёжек нужны; XBM используется;
Telegram Stars — как было (polling); «паранойя» не нужна: edge может быть взломан, главное — без доступа к панели и Remnawave.

| План | Сделано |
|---|---|
| Стелс-«стук» для панели | не делалось (не нужно); оставлено: `ssl_reject_handshake`, `noindex`, `no-referrer`, CSP, `server_tokens off` |
| AmneziaWG / режим «прыжок» / несколько edge | не делалось; обычный WireGuard (интерфейс `blinvpn`), один edge; архитектура позволяет добавить позже |
| Вебхук-режим Telegram | убран из установки: звёзды и бот — polling, как было; `/api/telegram/webhook` закрыт на обоих серверах |
| Очередь писем при недоступном edge | не делалось: письмо при недоступном edge возвращает ошибку (как и любая другая отправка) |
| Перенос старой установки | установщик панели принимает архив `data` и старый `.env` (переносит ключи шифрования и настройки, кроме адресов) |
| Маршрутизация в ingress по сайту | по пути (наборы путей мини-аппа, вебхуков и подписки не пересекаются); токен edge — `X-Edge-Token` (nginx, XBM) или `X-Api-Key` (subscription-page через `CADDY_AUTH_API_TOKEN`) |
| Белый список Remnawave для subpage | точный, по исходникам subscription-page 8.0.0: `/api/system/metadata`, `/api/subscription-page-configs[/uuid]`, `/api/subscriptions/subpage-config/{short}`, `/api/sub/{short}[/info|/{client}]` |

Файлы: `src/core/deploy.py` (роли, адреса, IP клиента, leakguard, клиент агента), `src/ingress/ingress.py`,
`edge/agent/agent.py`, `deploy/{panel,edge}/*.tpl`, `docker-compose.{panel,edge}.yml`, `scripts/install/*`.

## 0. Коротко: как всё будет устроено

```
                     ИНТЕРНЕТ (пользователи, Telegram, платёжки)
                                    │
        ┌───────────────────────────┼───────────────────────────────┐
        │ app.домен (мини-апп)       │ sub.домен (подписка)   hook.другой-домен (вебхуки)
        ▼                           ▼                               ▼
┌──────────────────────────────── СЕРВЕР 2: EDGE ("витрина") ──────────────────────────────┐
│ nginx :443  ── статика мини-аппа                                                          │
│             ── /api/app/*  ───────────────┐                                               │
│             ── страница подписки (rw subpage) ──┐                                         │
│             ── XBM (подписка для VPN-клиентов) ─┤                                         │
│             ── /platega … /2328 (9 платёжек), /tg/<секрет> ─┤                             │
│ edge-agent (только на wg-IP, команды от панели)  │                                         │
│ НЕТ: БД, токена бота, токена Remnawave, ключей платёжек, IP и домена панели               │
└──────────────────────────────────────────────────┼───────────────────────────────────────┘
                                                   │  WireGuard-туннель 10.213.0.0/24
                                                   │  (ПАНЕЛЬ сама звонит на edge,
                                                   │   edge не знает адрес панели)
┌──────────────────────────────── СЕРВЕР 1: PANEL ("сейф") ────────────────────────────────┐
│ edge-ingress 10.213.0.1:8443 — ЕДИНСТВЕННАЯ дверь из туннеля:                             │
│   белый список путей · чистка заголовков · подстановка токенов · сканер утечек           │
│      ├─► api-public  127.0.0.1:8001  (только /api/app/*, /api/support/file/*)             │
│      ├─► webhook     127.0.0.1:5000  (9 платёжек, Telegram)                               │
│      └─► Remnawave   127.0.0.1:3000  (только /api/sub/* и что нужно странице подписки)    │
│ api-panel 127.0.0.1:8000 (/api/panel/*, /api/internal/*) ◄─ nginx :443 панель (стелс)     │
│ bot (polling), monitor, Remnawave, БД SQLite, бэкапы                                      │
└───────────────────────────────────────────────────────────────────────────────────────────┘
```

Главные идеи (простыми словами):

1. **Пользователь общается только с edge.** Всё, что он видит (мини-апп, ссылка подписки, страница оплаты, письма, сообщения бота), указывает только на домены edge.
2. **Edge ничего не знает о панели.** Ни IP, ни домена. Панель сама подключается к edge по WireGuard («обратный туннель»). В конфиге edge есть только внутренний адрес `10.213.0.1`.
3. **Одна дверь в панель.** Всё, что приходит из туннеля, проходит через один маленький сервис `edge-ingress` на панели. Он пропускает только разрешённые пути, вычищает заголовки и проверяет каждый ответ: если в ответе вдруг есть IP или домен панели — ответ блокируется, а в форум летит тревога. Так даже будущая ошибка в коде не превратится в утечку.
4. **Edge считается «грязным».** Если edge взломают, злоумышленник получит только то, что и так видит пользователь. Секретов на edge нет; вебхуки проверяет панель своими ключами, которых на edge нет.
5. **Панель «невидимая».** Она на отдельном домене, не связанном с брендом. Без секретного «стука» отдаёт 404, на запросы по IP рвёт TLS, в поисковики не попадает.
6. **Вебхуки** — на отдельном домене (`hook.*`). DNS этого домена смотрит на edge (или на отдельный третий сервер с той же ролью), но **никогда** на панель.

### 1.2. Что сломается при разделении, если не учесть (ловушки)

| # | Ловушка | Что будет |
|---|---------|-----------|
| B1 | Все запросы придут с одного IP (edge) | Лимиты по IP (`emailcode_ip`: 10 за 5 мин) сработают на **всех пользователей сразу** — вход по почте ляжет. Капча, журнал входов, «новый вход с IP…» — всё сломается. |
| B2 | Два процесса API из одного `core.py` | На старте `core.py` запускает фоновые потоки: бэкапы, сверку платежей, синк XBM, автозакрытие поддержки, докачку рассылок, бэкфилл Remnawave. Во втором процессе это всё запустится **дважды**: двойные рассылки, двойные бэкапы, гонки в платежах. |
| B3 | Старт `_startup()` | Помечает рассылки `Sending` как `Interrupted`. Рестарт публичного процесса **прервёт рассылку**, которую шлёт панельный процесс. |
| B4 | Миграции БД | `db.init_db()` в двух процессах одновременно → гонка миграций («duplicate column»). |
| B5 | HWID-лимит Remnawave | Если туннель/фильтр потеряет заголовки `x-hwid`, `x-device-os`, `x-ver-os`, `x-device-model`, `user-agent`, лимит устройств перестанет работать (или начнёт всех блокировать). |
| B6 | IP пользователя в Remnawave | Remnawave пишет IP запроса подписки. Без правильного `X-Forwarded-For` там у всех будет IP edge. |
| B7 | Переписывание путей | `core.py:6117` сравнивает `request.url.path` с `_BANNED_ALLOWED_PATHS`. Если прокси поменяет путь (префикс), бан-логика сломается. **Пути не переписываем нигде.** |

## 2. Модель угроз: от чего защищаемся

**Что защищаем:** IP и домен сервера панели, доступ к панели, БД, токены (бот, Remnawave, ключи 9 платёжек, пароль «Мой налог»).

**От кого:**
- обычный пользователь / конкурент / РКН-исследователь, который хочет найти «мозг» сервиса;
- тот, кто взломал edge;
- тот, кто перехватывает трафик между серверами;
- бывший сотрудник или подкупленный модератор поддержки (частично, см. раздел 6.3).

**Гарантии после реализации:**
1. Ни в одном ответе, письме, сообщении бота или ссылке, которые доходят до пользователя, нет IP/домена панели. Это закрыто **конструкцией** (edge не знает адрес) и **проверкой** (сканер утечек на ingress).
2. Трафик между серверами шифруется WireGuard. Подменить его без ключа нельзя.
3. Взлом edge не даёт: доступ к `/api/panel/*`, БД, токенам, возможность выдать себе подписку через поддельный вебхук.
4. Падение edge не трогает панель, бота и уже настроенные VPN-подключения (ноды работают напрямую).

**Честно о пределах** (что технически невозможно гарантировать):
- Если edge взломан **с root**, злоумышленник увидит в `wg show` адрес, с которого подключается панель. Защита — **режим «прыжок»** (опция, раздел 4.6): панель подключается к edge через промежуточный сервер, и edge видит только его IP.
- Взломанный edge может подменить JS мини-аппа и воровать сессии пользователей. Это верно для любого сайта. Защита — минимум софта на edge, только ключи для SSH, автообновления, контроль целостности файлов.
- Сотрудники, которые входят в панель, знают её домен. Для максимума — доступ только через админский WireGuard/VPN (опция).

## 3. Архитектура

### 3.1. Домены (все спрашиваются при установке)

| Домен | Пример | DNS → | Кто видит | Требования |
|-------|--------|-------|-----------|------------|
| Мини-апп | `app.blinvpn.ru` | edge | все | — |
| Подписка | `sub.blinvpn.ru` (можно = мини-апп) | edge | все | Remnawave `SUB_PUBLIC_DOMAIN` = он |
| Вебхуки | `pay-cb.какой-то-другой.xyz` | edge (или отдельный relay) | платёжки, Telegram | **другой** регистрируемый домен, не похож на бренд |
| Панель BlinVPN | `cp.нейтральный-домен.net` | панель | только сотрудники | **не связан** с брендом, своё имя, без «blin/vpn» |
| UI Remnawave | `rw.нейтральный-домен.net` (опц.) | панель | только владелец | лучше вообще без домена: SSH-туннель |

Правила для доменов (их проверяет установщик):
- домен панели **не может** совпадать с доменами edge или быть их поддоменом и наоборот;
- у каждого домена **отдельный сертификат** (никаких SAN на несколько доменов: сертификат публикуется в CT-логах и связал бы домены);
- домен панели не содержит слов `blin`, `vpn` (предупреждение, можно продолжить);
- опция: сертификат панели через DNS-01 wildcard (`*.нейтральный.net`), тогда в CT-логах не будет конкретного поддомена.

### 3.2. Сервер 1 — PANEL (сейф)

| Компонент | Где слушает | Что делает |
|-----------|-------------|------------|
| nginx (хост) | `0.0.0.0:443` | только домен панели (+ опц. UI Remnawave), стелс-режим |
| `api-panel` (uvicorn, `API_ROLE=panel`) | `127.0.0.1:8000` | `/api/panel/*`, `/api/internal/*`, `/api/support/file/*`; **все** фоновые задачи |
| `api-public` (uvicorn, `API_ROLE=public`) | `127.0.0.1:8001` | только `/api/app/*`, `/api/support/file/*`, `/api/health`; **никаких** фоновых задач и миграций |
| `webhook` (`payments.webhooks:app`) | `127.0.0.1:5000` | 9 платёжек + Telegram (вебхук-режим) |

## 4. Связь между серверами

### 4.1. Почему WireGuard и почему «панель звонит сама»

- WireGuard: шифрование и взаимная аутентификация по ключам. Пакет без правильного ключа отбрасывается молча, порт не отвечает на сканирование.
- Панель — **инициатор**. В конфиге панели: `Endpoint = <IP edge>:<порт>`, `PersistentKeepalive = 25`. В конфиге edge у пира панели **нет Endpoint** — edge узнаёт адрес только из входящих пакетов и нигде его не хранит.
- У панели нет ни одного входящего порта для edge. Снаружи на панели открыты только 443 (панель, стелс) и 22.

Конфиг edge (пример, генерирует установщик):
```ini
[Interface]
Address    = 10.213.0.11/24
ListenPort = 4xxxx            # случайный высокий порт
PrivateKey = <edge priv>

[Peer]                         # панель
PublicKey  = <panel pub>
AllowedIPs = 10.213.0.1/32     # от этого пира принимаем ТОЛЬКО 10.213.0.1
# Endpoint отсутствует намеренно
```
Конфиг панели:
```ini
[Interface]
Address    = 10.213.0.1/24
PrivateKey = <panel priv>
# ListenPort не задан: панель ничего не слушает

[Peer]                         # edge-1
PublicKey  = <edge pub>
AllowedIPs = 10.213.0.11/32
Endpoint   = <edge IP>:4xxxx
PersistentKeepalive = 25
```

### 4.2. Слои защиты канала (снаружи внутрь)

1. **WireGuard**: шифрование + привязка «ключ ↔ IP в туннеле» (cryptokey routing). Пакет с `10.213.0.11` может прийти только от владельца ключа edge-1.
2. **nftables на панели**: на `wg0` разрешено только `10.213.0.0/24 → 10.213.0.1:8443/tcp`. Всё остальное (SSH, 3000, 8000, 8001, 5000) из туннеля закрыто.
3. **nftables на edge**: исходящее в `wg0` только на `10.213.0.1:8443`; входящее из `wg0` только `10.213.0.1 → 10.213.0.11:9443`.
4. **Токен edge** (`X-Edge-Token`, 256 бит, свой у каждого edge): nginx edge добавляет его к каждому запросу, ingress сверяет через `hmac.compare_digest`. Защищает, если когда-нибудь ingress по ошибке окажется доступен не только из туннеля.
5. **Подпись команд панель → edge-agent**: HMAC-SHA256 (`ts`, `nonce`, метод, путь, sha256 тела), окно ±60 с, nonce запоминается на 5 минут (защита от повтора). Нужна синхронизация времени: установщик включает `chrony`/`systemd-timesyncd`.

Почему не mTLS поверх WireGuard: даёт то же самое, но это ещё один набор сертификатов, которые надо ротировать, и ещё одно место для ошибок. Токен + HMAC внутри WG дают ту же глубину защиты проще.

### 4.3. Транспорт, если WireGuard блокируют

Если один из серверов в РФ, ТСПУ может резать WireGuard по сигнатуре рукопожатия. Установщик предложит транспорт:
- `wireguard` (по умолчанию, ядро, быстрее всего);
- `amneziawg` (тот же WireGuard с обфускацией: Jc/Jmin/Jmax/S1/S2/H1–H4; конфиги совместимы по логике).

Выбор хранится в `TUNNEL_TRANSPORT`. Вся остальная система от транспорта не зависит: ей нужен только интерфейс с `10.213.0.x`.

### 4.4. MTU и надёжность
- MTU `wg0` = 1420 (WireGuard) / 1280 (AmneziaWG), иначе большие загрузки в поддержку будут виснуть.
- `docker.service` стартует **после** `wg-quick@wg0` (systemd drop-in `After=`/`Wants=`), иначе ingress не сможет привязаться к `10.213.0.1` при загрузке. Вдобавок у контейнера ingress `restart: unless-stopped` и healthcheck.
- Монитор на панели раз в 30 с проверяет туннель (handshake не старше 3 минут и `GET /agent/health`). Если туннель лежит дольше 2 минут — тревога в форум-топик «ошибки». Восстановился — сообщение «восстановлено».

### 4.5. Несколько edge (на будущее, закладываю сразу)
- Каждый edge — отдельный WG-пир (`10.213.0.11`, `.12`, …), свой токен, своя запись в таблице `edges` (имя, pubkey, wg_ip, домены, версия, last_seen).
- Команды: `blinvpn edge add`, `blinvpn edge list`, `blinvpn edge revoke <имя>`. Revoke мгновенно удаляет пира и токен: взломанный edge сразу отрезан.
- Несколько edge с одним доменом = DNS round-robin или переключение A-записи. Это и есть отказоустойчивость витрины.

### 4.6. Режим «прыжок» (опция для паранойи)
Панель подключается к edge не напрямую, а через промежуточный хоп (отдельный дешёвый VPS или одна из своих нод): `panel → relay → edge`. На edge в `wg show` тогда виден только IP relay. Делается вторым WG-интерфейсом и маршрутом на `Endpoint` edge через relay. В первой версии это опция, а не обязательная часть.

## 5. Маршрутизация запросов

### 5.1. nginx на edge (по доменам)

**app.домен:**
| Путь | Метод | Куда | Лимит тела |
|------|-------|------|------------|
| `/` (статика, SPA) | GET | `127.0.0.1:9741` | — |
| `/redirect.html` | GET | `127.0.0.1:9741`, без access_log | — |
| `/api/app/support/upload` | POST | ingress | 55m |
| `/api/app/*` | GET/POST/PUT/DELETE | ingress | 1m |
| `/api/support/file/*` | GET | ingress | — |
| `/api/health` | GET | **локальный ответ edge** (не ходит в панель) | — |
| `/api/panel`, `/api/internal`, `/api/telegram`, всё остальное в `/api/` | любой | **404 локально** | — |

**sub.домен:**
| Условие | Куда |
|---------|------|
| User-Agent VPN-клиента (Happ, v2rayN, Clash/mihomo, sing-box, Hiddify, Streisand, Incy…) | XBM `127.0.0.1:4100` |
| Браузер | subpage `127.0.0.1:3010` |
| `/api/sub/*` с `?raw=1` и т.п. | по правилам XBM (как сейчас в `tools/nginx_xbm.py`) |

**hook.другой-домен:**
| Путь | Куда | Доп. защита на edge |
|------|------|---------------------|
| `POST /platega`, `/cispay`, `/yookassa`, `/lava`, `/paypalych`, `/rollypay`, `/wata`, `/heleket`, `/2328` | ingress → webhook | `limit_req` (≈ 5 r/s на IP, burst 20), тело ≤ 64k, **без** изменения тела (`proxy_request_buffering on`, никакого gzip/перекодирования) |
| `GET` на те же 9 путей | локальный `200 {"ok":true}` на edge (платёжки так проверяют адрес, панель для этого не нужна) | — |
| `POST /yookassa` | дополнительно: allow только сети ЮKassa (тот же список, что `yookassa.NOTIFY_NETS`), остальным 403 прямо на edge | — |
| `POST /tg/<секретный-путь>` | ingress → webhook (Telegram) | allow только `149.154.160.0/20`, `91.108.4.0/22` |
| всё остальное | 404 | — |

Список путей платёжек на edge генерируется из одного источника — `payments_config.SPECS[*]["webhook"]` (панель отдаёт его в коде сопряжения и при обновлении через agent). Тогда новая платёжка не потеряется: добавил в `SPECS`, и путь появился и на edge, и в ingress.

**default_server** (запрос по IP или с чужим именем): `listen 443 ssl default_server; ssl_reject_handshake on;` и `:80 → return 444`.

Общие настройки nginx edge:
- `server_tokens off`, свои JSON-страницы ошибок для 502/503/504: `{"detail":{"message":"Сервис временно недоступен, попробуйте через минуту"}}`. Наружу ни слова о том, что за nginx стоит что-то ещё.
- Перед `proxy_pass` в ingress **вычистить** все клиентские заголовки, связанные с IP: `X-Forwarded-For`, `X-Real-IP`, `Forwarded`, `CF-*`, `True-Client-IP`, `X-Client-IP`, `X-Cluster-Client-IP`, `X-Edge-*`, `X-Blin-*` (через `proxy_set_header ... ""`).
- Выставить свои: `X-Blin-Client-IP: $remote_addr`, `X-Blin-Site: app|sub|hook`, `X-Blin-Proto: https`, `X-Edge-Token: <токен>`.
- `proxy_hide_header` для `Server`, `X-Powered-By`, `Via`, `X-Upstream*`.
- `proxy_connect_timeout 5s`, `proxy_read_timeout 60s` (загрузки — 300s), `proxy_next_upstream off` (иначе POST платежа может повториться дважды).

### 5.2. edge-ingress на панели (политики)

Это маленький сервис (Starlette + httpx, ~400 строк, покрыт тестами). Порядок обработки запроса:

1. **Источник**: TCP-пир должен быть из `10.213.0.0/24` и совпадать с известным edge. Иначе 403.
2. **Токен**: `X-Edge-Token` → определяем, какой это edge. Неверный токен → 403 + тревога (раз в 10 минут, без спама).
3. **Нормализация пути**: отклонять (400) пути с `..`, `//`, `%2e`, `%2f`, `%5c`, `\`, нулевыми байтами, `;`, двойным кодированием. Проверка идёт по `raw_path`, а не по уже декодированному.
4. **Белый список** (сайт × метод × регулярка пути). Всё, чего нет в списке, → 404:
   - `app`: `^/api/app/[a-z0-9/_-]+$` (GET/POST/PUT/DELETE), `^/api/support/file/[A-Za-z0-9_-]+$` (GET) → `127.0.0.1:8001`;
   - `hook`: `^/(platega|cispay|yookassa|lava|paypalych|rollypay|wata|heleket|2328)$` (POST; список строится из `payments_config.SPECS`) → `127.0.0.1:5000/<тот же путь>`; `^/tg/<секрет>$` (POST) → `127.0.0.1:5000/telegram`;
   - `sub`: `^/api/sub/[A-Za-z0-9_-]{6,64}(/[a-z0-9-]+)?$` (GET) + ручки, которые нужны subscription-page (точный список снимаю с исходников той версии subpage, что ставим; всё неизвестное → 404 и лог) → `127.0.0.1:3000`.
5. **Заголовки запроса — белый список.** Пропускаем: `content-type`, `content-length`, `accept`, `accept-language`, `user-agent`, `authorization` (только для `app`, это сессия мини-аппа), `x-telegram-init-data`, `x-app-session`, `x-hwid`, `x-device-os`, `x-ver-os`, `x-device-model`, `if-none-match`. Для сайта `hook` — **свой список на каждый путь** (B13): `/platega` → `x-merchantid`, `x-secret`; `/cispay`, `/wata` → `x-signature`; `/rollypay` → `x-signature`, `x-timestamp`; `/lava` → `authorization`, `signature`; `/heleket`, `/2328`, `/paypalych`, `/yookassa` → подпись в теле, доп. заголовков нет; `/tg/*` → `x-telegram-bot-api-secret-token`. Всё остальное выбрасываем. Тело передаётся **байт-в-байт** (B14), `content-type` сохраняется как есть (у PayPalych бывает и form, и JSON).
6. **IP клиента**: из `X-Blin-Client-IP` (проверить, что это валидный IP) делаем ровно один доверенный заголовок `X-Real-IP` для api-public/webhook и `X-Forwarded-For: <ip>` для Remnawave.
7. **Подстановка токена Remnawave** для `sub`: `Authorization` из запроса edge выбрасывается, ставится настоящий токен с панели. Лучше **scoped read-only токен** (Remnawave ≥ 2.8.0 умеет scoped-токены: `subscriptions:read`, `subscription-pages:read`, `metadata:read`, …). Edge держит фиктивный токен нужного формата, чтобы subpage запустилась.
8. **Лимиты**: размер тела (1 МБ / 55 МБ для upload / 64 КБ для hook), таймауты, не больше N одновременных запросов на edge (семафор) — флуд через edge не уронит панель.
9. **Сканер утечек ответа** (сердце защиты):
   - чёрный список строк: публичные IPv4/IPv6 панели (автоопределение + `.env`), `PANEL_DOMAIN`, `REMNAWAVE_UI_DOMAIN`, hostname панели, `127.0.0.1:3000`, `remnawave:3000`, `LEAK_GUARD_EXTRA` (свой список);
   - проверяются все заголовки ответа и тело для `application/json`, `text/*`, `application/yaml` и т.п. (до 5 МБ, без учёта регистра);
   - бинарные ответы (вложения поддержки: картинки, видео, pdf) не сканируются: это файлы, которые загрузили сами пользователи/сотрудники, и их содержимое проверяется при загрузке (см. 6.2, п. 19);
   - нашёл → **ответ не уходит**, клиенту `503` с общим текстом, в форум «🚨 УТЕЧКА ЗАБЛОКИРОВАНА: путь, что найдено (замаскировано)», счётчик в мониторинге.
10. **Заголовки ответа**: выбросить `server`, `x-powered-by`, `via`, `date`(оставить), всё `x-*` кроме известных; для `sub` пропустить заголовки подписки (`subscription-userinfo`, `profile-title`, `profile-update-interval`, `support-url`, `profile-web-page-url`, `announce`, `routing`, `content-disposition`, `hide-settings` …), каждый тоже через сканер.
11. **Журнал**: метод, путь (без query с токенами), статус, время, edge. IP пользователя не логируем дольше суток.

### 5.3. Remnawave и XBM

- XBM на edge: `REMNAWAVE_URL=http://10.213.0.1:8443` + заголовки `X-Edge-Token`, `X-Blin-Site: sub`. Это небольшая правка `xbm/src/server.js fetchUrl`: добавить статические заголовки из env `UPSTREAM_EXTRA_HEADERS`.
- XBM передаёт IP клиента вверх. Сейчас он доверяет `x-forwarded-for` от клиента (`server.js:292`), а на edge перед XBM стоит наш nginx. Значит, nginx edge перед XBM тоже чистит и ставит `X-Real-IP $remote_addr`, а XBM берёт **только** его.
- `forwardResponseHeaders` в XBM: заменить чёрный список на **белый** (заголовки подписки + content-type/disposition).
- Конфиг XBM (`panel.json`): `_xbm_sync_loop` на панели пушит его через edge-agent: `PUT /agent/xbm/config`, подпись HMAC. Agent атомарно пишет файл (tmp + rename), XBM подхватывает сам (`panel-config.js` уже следит за файлом). Если пуш не прошёл — повтор с backoff, тревога после 10 минут.
- Проверки XBM из панели (`/api/panel/xbm/check`, `health`) идут через agent: `GET /agent/xbm/health`, `POST /agent/xbm/check`.
- Кэш XBM — подарок для отказоустойчивости: если панель недоступна, VPN-клиенты получают последнюю успешную подписку из кэша. TTL кэша сделать настраиваемым (по умолчанию 24 ч на «аварийную» отдачу).

### 6.3. Операционные (правила, которые выводит установщик и которые записаны в README)

- Сервер панели — у **другого хостера** и в другой подсети, чем edge (соседей по /24 сканируют).
- На IP панели больше ничего публичного не держать: ни сайтов, ни других проектов.
- PTR (rDNS) панели — нейтральный или дефолтный хостерский.
- SSH на панели: только ключи, `PasswordAuthentication no`, желательно allowlist по IP админа или доступ через админский WireGuard-пир.
- Форум-группа уведомлений — только сотрудники.
- Сотрудникам поддержки, которым не нужно, лучше не давать роль, видящую настройки инфраструктуры (это уже есть в `access.ts`, проверю).

## 7. Вебхуки на отдельном домене

- Установщик панели спрашивает `WEBHOOK_DOMAIN` (обязательно ≠ домен мини-аппа, ≠ домен панели, другой регистрируемый домен рекомендуется).
- DNS вебхук-домена → edge (по умолчанию тот же edge, отдельный `server {}` и отдельный сертификат) **или** отдельный маленький сервер с ролью `edge` в режиме `hook-only` (тот же установщик, отвечает только на вебхуки).
- Сейчас вебхуки принимает пакет `src/api/payments/webhooks/` (сервис `payments.webhooks:app`, 9 роутеров). Пути: `/platega`, `/cispay`, `/yookassa`, `/lava`, `/paypalych`, `/rollypay`, `/wata`, `/heleket`, `/2328`.
- Кому что вписать:
  - в кабинет (Platega, cisPay, ЮKassa, PayPalych, RollyPay, WATA): `https://<WEBHOOK_DOMAIN>/<путь>`. Установщик печатает все 9 в конце, панель показывает их во вкладке «Платежи» (`payments_config.webhook_url`);
  - Lava, Heleket, 2328 передают URL **в каждом счёте**, вписывать никуда не надо. Поэтому для них `PUBLIC_WEBHOOK_URL` обязателен (A12).
- Telegram (если включён вебхук-режим): `https://<WEBHOOK_DOMAIN>/tg/<32 случайных символа>` + `secret_token`. Секрет и путь хранятся **только на панели**; на edge — только путь в nginx (он не секретный сам по себе, проверку `secret_token` делает панель). Сейчас вебхук Telegram обрабатывает `core.py:7298` (`/api/telegram/webhook`). Переношу его в сервис вебхуков рядом со `stars_webhook.py`, чтобы `api-public` не принимал апдейты Telegram.
- Проверки подписей во всех 9 модулях остаются как есть: они делаются на панели, ключей на edge нет. Меняю только `client_ip()` в `payments/webhooks/common.py` (A11): верить `X-Real-IP`, только если пир — `127.0.0.1` (ingress), иначе брать адрес пира; `X-Forwarded-For` не читать вообще.
- Лимит частоты на hook-пути (A13) — на edge (`limit_req`) и в ingress; в `wata.py` принудительное обновление ключа не чаще раза в минуту.
- **Исправление A5:** вводится единый режим доставки апдейтов Telegram:
  - `TELEGRAM_UPDATES=polling` (по умолчанию и рекомендовано: никаких входящих, нечего атаковать) — бот поллит, вебхук не регистрируется;
  - `TELEGRAM_UPDATES=webhook` — бот **не** поллит и **не** вызывает `deleteWebhook`. Апдейты приходят в `webhook`-сервис, тот обрабатывает Stars сам, а остальное кладёт в очередь в БД (`tg_updates`), откуда их забирает бот (тот же `process_update`). Один источник правды, никакого 409.
  - Установщик при смене режима сам вызывает `setWebhook`/`deleteWebhook`.
- Тайм-аут Telegram на `pre_checkout_query` — 10 секунд. Цепочка edge → ingress → webhook добавляет мало, но таймауты в цепочке ставлю 8 с, чтобы успеть ответить.

## 9. Репозиторий

**Рекомендация: один репозиторий, две роли.** Почему не два:
- код не секретный (доменов и ключей в нём нет — они в `.env` на серверах);
- главный источник багов при двух репо — **рассинхрон версий** (поменял API в одном, забыл в другом). В одном репо изменение протокола делается одним коммитом и одним тестом;
- проще CI и тесты контракта «ingress ↔ edge».

Чтобы на edge не лежал лишний код: установщик edge делает `git clone --filter=blob:none --sparse` + `git sparse-checkout set src/app src/site assets edge xbm deploy/edge scripts/install`. Исходников панели на edge физически нет.

Протокол версионируется: `EDGE_PROTOCOL=1` в коде обеих ролей. Agent и ingress отдают версию; при несовпадении мажорной версии панель показывает «обновите edge», а ingress продолжает обслуживать старую версию, пока она поддерживается (обратная совместимость на одну версию).

Если всё-таки захочешь отдельный репо (например, публичный edge и приватная панель) — структура `edge/` + `deploy/edge/` уже будет самодостаточной, вынести её — час работы. Решать тебе (вопрос в разделе 15).

Структура после изменений:
```
install.sh                 # диспетчер: спрашивает роль (panel / edge) или --role=
scripts/install/
  lib.sh                   # общие функции (prompt, env, certbot, nginx, ufw/nft, docker)
  panel.sh                 # установка/обновление панели
  edge.sh                  # установка/обновление edge
  pair.sh                  # коды сопряжения
deploy/
  panel/docker-compose.yml, nginx/panel.conf.tpl, wg/
  edge/docker-compose.yml,  nginx/edge.conf.tpl,  wg/
src/
  core/ api/ bot/ panel/   # панель (как сейчас) + leakguard.py, edge_agent_client.py
  ingress/                 # edge-ingress (только на панели)
  app/ site/               # мини-апп (собирается на edge)
edge/agent/                # edge-agent (только на edge)
xbm/                       # (только на edge)
```

## 10. Установка

### 10.1. Порядок

1. Купить **новый** сервер под панель (см. раздел 11) и сервер под edge.
2. DNS: `app`, `sub`, `hook` → IP edge; домен панели → IP панели. Подождать обновления DNS.
3. Установить Remnawave на сервер панели (если ещё нет) **без** subscription-page и без его nginx на 443.
4. `install.sh` на панели → в конце выдаёт **код сопряжения** и ждёт.
5. `install.sh` на edge → вставить код → edge выдаёт **ответный код**.
6. Вставить ответный код на панели → туннель поднимается → автоматические проверки → готово.

### 10.2. Установщик панели (по шагам)

1. Проверки: root/sudo, Ubuntu/Debian, свободны 80/443 (`ss -ltnp`; если занято контейнером `remnawave-nginx`/`caddy` — объяснить, что делать), есть ≥ 2 ГБ RAM, время синхронизировано (включить `systemd-timesyncd`).

4. Автоопределение публичных IP панели (интерфейсы + `ip route get` + внешний echo-сервис) → `PANEL_PUBLIC_IPS` в `.env` (для сканера утечек). Показать и спросить «всё верно?».
5. Проверки доменов (`validate_domains`): все различаются; панель не поддомен edge-доменов и наоборот; edge-домены не резолвятся в IP панели (**если резолвятся — СТОП**, это и есть утечка); домен панели резолвится в IP панели.

Проверить, что Remnawave слушает только `127.0.0.1` (`ss`), иначе предупредить и предложить исправить `ports:` в его compose. Если на сервере есть контейнер `remnawave-subscription-page` — предложить остановить (его место на edge).
7. Сертификат только для домена панели (и UI Remnawave). Отдельно на каждый.
8. Генерация секретов: `INTERNAL_API_SECRET`, `PANEL_SETUP_TOKEN`, `MONITOR_SECRET_KEY`, `TELEGRAM_WEBHOOK_SECRET`, `TG_HOOK_PATH`, WG-ключи панели, токен edge-1, HMAC-ключ agent-1, секрет «стука» панели.
9. `.env` (600) + nginx из шаблона + `nginx -t`.
10. nftables (см. 10.5). Docker: `"iptables": true` оставляем, но все порты только на `127.0.0.1`; проверка `ss` после запуска.
11. `docker compose build` (с повторами, как сейчас) → `up -d` → дождаться healthcheck `api-panel`, затем `api-public`.
12. Логин/пароль панели (как сейчас: показать один раз и удалить файл) + **секретная ссылка входа** (стук).
13. **Код сопряжения**: `BLINPAIR1.<base64url(json)>.<crc>`. Внутри: версия протокола, pubkey панели, wg-подсеть и адреса (`10.213.0.1`, `10.213.0.11`), порт ingress, токен edge, HMAC-ключ agent, домены edge, username бота, транспорт (+ параметры AmneziaWG), путь `/tg/<…>`, ветка/коммит репо. **Нет**: IP панели, домена панели, токенов бота/Remnawave/Platega. Выводится один раз; рядом — предупреждение «это секрет, не пересылайте в мессенджерах».
14. Ждёт ввода **ответного кода** (можно выйти и потом выполнить `blinvpn pair finish`).
15. Ответный код: `BLINEDGE1.<base64url(json)>.<crc>` — pubkey edge, публичный IP:порт edge, версия. Панель прописывает пира с Endpoint, `wg-quick up`, ждёт handshake.
16. **Итоговые проверки** (каждая с понятным текстом при провале):
    - handshake есть; `GET /agent/health` ок; версии совпадают;
    - через edge-agent запросить публичный `https://app.домен/api/health` **с самого edge** (agent делает запрос к себе локально по SNI) — проверяем, что nginx edge настроен, не светя панель;
    - через agent: `GET https://app.домен/api/app/config` на edge → дошло до api-public и вернулось → сканер не сработал;
    - через agent: запрос подписки тестового пользователя через `sub.домен` → в ответе ссылки на `sub.домен`, нет утечек;
    - XBM health через agent;
    - тестовая утечка: ingress в спец-режиме проверки отдаёт тело с `PANEL_DOMAIN` → должен вернуть 503 (проверяем, что сканер жив).
17. Финальная сводка: адреса, URL вебхуков всех 9 платёжек (с пометкой, какие вписывать в кабинет, а какие передаются в счёте), что вписать в @BotFather (`/setdomain` и Web App URL = мини-апп), правила из 6.3.

### 10.3. Установщик edge (по шагам)

1. Проверки: свободны 80/443, синхронизация времени.

### 10.4. Обновление
- Панель: `install.sh` → «Обновить» (как сейчас: fetch → reset → свежий скрипт → пост-обновление). Пост-обновление на панели также может обновить edge командой через agent (`POST /agent/update`: agent делает `git pull` по sparse-checkout и `compose up -d --build`) — по желанию, с подтверждением.
- Порядок всегда: **сначала панель, потом edge** (панель поддерживает протокол N и N−1).
- Миграции `.env` (как `migrate_security_update` сейчас) — для обеих ролей отдельно.

### 10.5. Файрвол (nftables, генерирует установщик)

**Панель:**
```
input:  policy drop
  lo accept; established,related accept; icmp(лимит) accept
  tcp dport 22 accept           (опц. только с ADMIN_IPS)
  tcp dport {80,443} accept     (опц. только ADMIN_IPS / Cloudflare)
  iifname "wg0" ip saddr 10.213.0.0/24 ip daddr 10.213.0.1 tcp dport 8443 accept
  iifname "wg0" drop            (явно, для читаемости)
forward: docker сам управляет своими цепочками; проверяем, что ничего не опубликовано не на 127.0.0.1
```
**Edge:**
```
input:  policy drop
  lo, established, icmp
  tcp dport 22 accept; tcp dport {80,443} accept
  udp dport <WG_PORT> accept
  iifname "wg0" ip saddr 10.213.0.1 tcp dport 9443 accept
output (wg0): только ip daddr 10.213.0.1 tcp dport 8443 + ответы
```
UFW, если он активен, установщик не ломает: либо переводит правила в nftables с подтверждением, либо добавляет эквивалентные правила в UFW (решу при реализации по тому, что стоит на серверах; по умолчанию — UFW, если он уже включён).

### 10.6. Замена доменов
- Домены edge: меняются на панели (`.env`, `PUBLIC_*`), затем команда через agent перевыпускает сертификаты и nginx на edge. Telegram/BotFather — подсказка.
- Домен панели: только на панели.
- Проверки 10.2-5 повторяются.

## 11. Миграция текущей установки (важно!)

**Текущий сервер уже «засвечен»:** домен мини-аппа годами указывал на его IP. Это осталось в истории DNS (SecurityTrails, ViewDNS), в логах Telegram-клиентов, у Platega, в CT-логах сертификатов, а у Remnawave — в ссылках подписки. **Если оставить панель на нём, вся схема бессмысленна.**

План миграции:
1. Новый сервер (другой хостер/подсеть) = **панель**. Чистый IP, нигде не светился.
2. Старый сервер = **edge** (пользователи и так знают его IP; старые ссылки подписки продолжат работать).
3. Шаги:
   1. На новом сервере: установить Remnawave, восстановить его БД из бэкапа старого (`pg_dump`/`pg_restore`), перенести `.env` Remnawave, поменять `SUB_PUBLIC_DOMAIN`.
   2. На новом сервере: `install.sh --role=panel --migrate`, перенести `data/` BlinVPN (БД SQLite через `sqlite3 .backup`, `data/dkim`, вложения поддержки), `.env` (установщик переразметит переменные).
   3. **Ноды Remnawave**: в их файрволе разрешить новый IP панели (Remnawave-панель сама подключается к нодам). Ноды мониторинга (`blinmon`) — тоже.
   4. Окно техработ: остановить старые `api/bot/webhook` → финальная синхронизация БД → запуск на новом.
   5. Старый сервер: снести панельные контейнеры, Remnawave, БД; поставить `install.sh --role=edge`; сопряжение.
   6. Сменить пароль панели, `INTERNAL_API_SECRET`, токены Remnawave (старый токен мог остаться на старом сервере), секреты вебхуков. В кабинетах Platega, cisPay, ЮKassa, PayPalych, RollyPay, WATA — новый URL вебхука на hook-домене. Ключи платёжек лучше перевыпустить: они лежали на старом сервере, который теперь станет «грязным» edge. Пароль «Мой налог» — тоже сменить.
   6a. Перед остановкой старой панели дождаться, пока очередь `nalogo_receipts` опустеет (нет строк `pending`/`cancel_pending`), иначе чек может уйти дважды: со старого сервера и с нового.
   7. Старый домен панели (если он был связан со старым IP) — **не использовать** для новой панели. Новый нейтральный домен.
4. Перенос данных между серверами — **через свой компьютер** (скачать бэкап → залить), а не `scp` с сервера на сервер (иначе в логах сервера останется IP другого).

## 12. Отказоустойчивость

| Что упало | Что происходит | Что видит пользователь |
|-----------|----------------|------------------------|
| Edge | Панель, бот, Remnawave, VPN-ноды работают. Монитор шлёт тревогу. | Мини-апп не открывается; **VPN работает** (ноды напрямую); бот отвечает. |
| Панель | Edge отдаёт статику мини-аппа; `/api/app/*` → красивая JSON-заглушка; XBM отдаёт подписку **из кэша**. | Экран «техработы, попробуйте позже»; VPN работает; обновление подписки — из кэша. |
| Туннель | Как «панель упала» для пользователей; WG сам переподключается (keepalive). | То же. |
| Edge взломан | `blinvpn edge revoke` → пир и токен удалены за секунды. Поднять новый edge (установщик ~10 мин), переключить DNS. | Короткий простой. |
| Утечка поймана сканером | Ответ не отдан, тревога, детали в форум. | Один запрос получил 503. |

Плюс: два процесса API (panel/public) — флуд мини-аппа не мешает работе панели.
Бэкапы: как сейчас (S3) + бэкап `.env` панели и WG-ключей **в зашифрованном виде** в тот же S3 (опция).

## 13. Как предотвращу баги и ошибки

### 13.1. Тесты (были в `tests/`, из поставки убраны)

1. **Роли API:** для каждой ручки из `app.routes` — доступна ли в panel/public. Тест «нет пересечений, кроме `/api/support/file`, `/api/health`», «в public нет ни одной `/api/panel`», «новая ручка без явного решения валит тест».
2. **Фоновые задачи:** при `API_ROLE=public` не запускается ни один поток (проверка `threading.enumerate()` после старта TestClient).
3. **`_client_ip`:** таблица кейсов: подделанные `CF-Connecting-IP`/`XFF`/`True-Client-IP` игнорируются; доверенный `X-Real-IP` только от `127.0.0.1`.
4. **Ingress:** белый список (≥ 60 кейсов: `..`, `%2e%2e`, `%2f`, `//api/panel`, `/api/app/../panel`, `/API/PANEL`, `\`, `;`, `%00`, длинные пути, неверные методы); заголовки (лишние выброшены, `x-hwid` прошёл); токен (неверный/пустой/чужой edge); сканер (IP/домен в JSON, в заголовке, в разном регистре, в URL-encoded виде → 503); лимиты тела; таймауты.
5. **leakguard:** чёрный список собирается правильно; нет ложных срабатываний на частях слов (домен `cp.example.net` не должен ловить `cp.example.network`... и наоборот должен ловить `https://cp.example.net/`) — граница токена.
6. **Публичные URL:** `subscription_url_for` никогда не возвращает хост ≠ `PUBLIC_SUB_URL` (property-тест на разных ответах Remnawave).
7. **Почта:** в split-режиме `smtplib` не вызывается на панели (мок, который падает при вызове).
8. **Telegram-режимы:** в webhook-режиме бот не вызывает `deleteWebhook`/`getUpdates`.
8a. **Вебхуки платёжек через ingress:** для каждой из 9 платёжек взять реальный пример уведомления (с подписью, посчитанной тестовым ключом), прогнать через ingress → сервис вебхуков → подпись принята. Тело байт-в-байт (B14), нужные заголовки дошли (B13), лишние выброшены. PayPalych — оба варианта: form и JSON. ЮKassa — IP из `X-Real-IP` от ingress принят, подделанный `X-Forwarded-For` игнорируется.
8b. **Чеки «Мой налог» (A10):** два процесса одновременно вызывают `process_queue` на одной строке → `income().create` (мок) вызван ровно 1 раз. Падение между create и update → строка в `sending`, повтор **не** отправляет вслепую.
8c. **URL вебхуков:** без `PUBLIC_WEBHOOK_URL` Lava/Heleket/2328 выдают понятную ошибку, а не URL мини-аппа (A12).
9. **Тест-сторож исходящих вызовов:** статический анализ (AST) всех `urlopen`/`smtplib`/`socket.create_connection` в коде панели — новый вызов без записи в разрешённый список валит тест.
10. **Тест-сторож «панель не ходит на edge через интернет»:** в коде панели нет обращений к `PUBLIC_APP_URL`/`PUBLIC_SUB_URL`/`PUBLIC_WEBHOOK_URL` как к адресу запроса (они только для генерации ссылок).
11. **E2E (docker compose в CI):** поднять panel + edge в двух сетях с WG между ними (userspace `wireguard-go` в контейнерах), мок Remnawave и Telegram, пройти сценарии: открыть мини-апп, auth, получить подписку, оплатить (мок Platega → вебхук через hook-домен), загрузить файл в поддержку, панель недоступна → заглушка, XBM из кэша. После каждого шага — grep всех ответов и логов edge на строки из чёрного списка → должно быть 0.
12. **XBM:** существующие `node --test` + новые на заголовки и `X-Real-IP`.
13. **Bash:** `shellcheck` для всех скриптов установки; `bash -n`; тест генерации/разбора кодов сопряжения (bats или python).
14. **nginx:** `nginx -t` на сгенерированных шаблонах в CI (контейнер nginx).

### 13.2. Правила при написании кода
- Никаких heredoc-конфигов длиннее 10 строк в bash → шаблоны + `envsubst` с явным списком переменных.
- Все секреты сравниваются через `hmac.compare_digest`.
- Всё, что «не знаю что это», → отказ (fail-closed): неизвестная роль, неизвестный путь, неизвестный заголовок, непрошедшая валидация URL.
- Пути не переписываются нигде на пути edge → ingress → api.
- Таймауты на каждом сетевом вызове.
- `proxy_next_upstream off` для POST (без двойных платежей).
- Логи без секретов и токенов (query string с `sig` в `/api/support/file` маскируется).
- Каждая новая переменная `.env` — в миграции установщика (иначе обновление старых установок упадёт).

### 13.3. Ручной чек-лист перед релизом
- [ ] `curl -k https://<IP панели>` → TLS рвётся.
- [ ] `curl https://<домен панели>/` без стука → 404; со стуком → панель.
- [ ] `curl https://app.домен/api/panel/auth/me` → 404 от edge.
- [ ] `curl -H 'CF-Connecting-IP: 1.1.1.1' …` → IP в журнале входа реальный.
- [ ] grep по всем файлам на edge (`/etc`, `/opt`, `/root`, `/var/log`, docker inspect) — нет IP/домена панели (скрипт `blinvpn audit-edge` в установщике, который запускается **на edge** и принимает строки для поиска только вводом с клавиатуры, нигде их не сохраняя).
- [ ] Письмо входа на свой ящик → в заголовках нет IP панели.
- [ ] Ссылка подписки, deep-link Happ/Incy, redirect.html → только edge-домены.
- [ ] Тестовый платёж **в каждой включённой платёжке** → вебхук прошёл через hook-домен, подпись принята, подписка выдана.
- [ ] ЮKassa: POST на `/yookassa` с чужого IP → 403 на edge; с поддельным `X-Forwarded-For` → тоже 403.
- [ ] Оплата через ЮKassa → ровно **один** чек в «Мой налог».
- [ ] Остановить панель → мини-апп показывает заглушку, Happ обновляет подписку из кэша.
- [ ] `edge revoke` → edge сразу 503, панель цела.

**Решения, принятые в плане (не передумывать без причины):**
- WG-подсеть `10.213.0.0/24`: панель `.1`, edge `.11+`. Ingress `10.213.0.1:8443`, agent `10.213.0.1x:9443`. Порты сделать настраиваемыми.
- Панель — WG-инициатор, у edge нет Endpoint пира.
- Ingress — единственная точка входа из туннеля; api-public слушает `127.0.0.1:8001`, принимает только с `127.0.0.1`.
- Remnawave-токен для subpage подставляет ingress; на edge — фиктивный.
- Почта — только через edge-agent в split-режиме.
- Telegram: `TELEGRAM_UPDATES=polling|webhook`, без конфликтов.
- Один репозиторий + sparse checkout на edge; `EDGE_PROTOCOL` версия.
- Коды сопряжения `BLINPAIR1.` / `BLINEDGE1.` без адреса панели.
- Порядок обновления: панель → edge; совместимость N/N−1.
- Шаблоны nginx файлами, не heredoc; `envsubst` с явным списком переменных (иначе `$host`/`$remote_addr` nginx будут съедены).

**Подводные камни, о которых легко забыть:**
- `envsubst` без списка переменных уничтожит `$host`, `$remote_addr` в nginx-шаблонах.
- `proxy_set_header` в nginx наследуется, только если в location нет своих `proxy_set_header` → выносить общий набор в `include`-файл и включать в каждый location.
- `add_header` тоже не наследуется в location со своим `add_header` → security headers через `include` в каждом location (или `always` + отдельный snippet).
- docker публикует порты мимо UFW/nftables → проверять `ss -ltnp` после `up`.
- `wg-quick` до docker при загрузке (systemd drop-in), иначе bind на `10.213.0.1` упадёт.
- Время: HMAC с окном ±60 с → NTP обязательно.
- Платёжный callback не должен ретраиться nginx-ом (`proxy_next_upstream off`).
- Platega `PLATEGA_WEBHOOK_IPS` и ЮKassa `ip_allowed` сравнивают с `common.client_ip` → должен быть реальный IP платёжки (от ingress), а не edge и не подделанный XFF.
- Подписи платёжек считаются по сырому телу: на edge и в ingress тело не трогать (без gzip, перекодировки, нормализации JSON); `proxy_request_buffering on`, но без модификации.
- Новый провайдер добавляется в `payments_config.SPECS` → путь должен автоматически попасть в nginx edge и белый список ingress (генерация из одного источника).
- Remnawave пишет IP запроса подписки — передать `X-Forwarded-For` реального клиента от ingress.
- HWID-заголовки (`x-hwid`, `x-device-os`, `x-ver-os`, `x-device-model`) и `user-agent` — в белых списках nginx edge, XBM и ingress.
- `subscriptions.key_config` в БД хранит старые URL подписки — при миграции переписать хост на `PUBLIC_SUB_URL` (и проверить сканером).
- Ответ `/api/support/file` при S3 — 302 на presigned URL S3 (это адрес S3, не панели — ок; но сканер должен проверять и заголовок `Location`).
- `TELEGRAM_INITDATA_MAX_AGE` в install = 86400, а дефолт в коде 3600 — не трогаю, просто помню.
- Скрипт `audit-edge` не должен сохранять искомые строки на edge (ввод с клавиатуры, без истории: `read -s`, `HISTFILE` не трогается, т.к. это `read`, а не команда).
- В e2e нельзя использовать реальные домены/IP.
- `api-public` не должна иметь доступ на запись к `data/backups`, `data/dkim` — смонтировать `data/` целиком нельзя избежать (SQLite), но отдельные секреты (dkim) вынести из `data/` в `secrets/` и монтировать только в api-panel.
